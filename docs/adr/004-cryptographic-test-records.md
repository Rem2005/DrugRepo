# ADR 004: Cryptographic Integrity of Test Records

## Status
Accepted

## Context
To support documentation under Section 63 of the BSA 2023, data must be highly resistant to tampering. A simple software hash is insufficient because compromised root access on an Android device could theoretically rewrite historical records and recalculate the hashes silently.

## Decision
We will implement an offline hash-chain ledger. Every record's SHA-256 hash will inherently include the previous_record_hash, computed over canonical JSON (RFC 8785) as specified in architecture.md §6. Furthermore, the record hash will be digitally signed (ECDSA secp256r1). The architecture explicitly prefers StrongBox KeyMint hardware, safely falls back to the Trusted Execution Environment (TEE), and strictly rejects software-only execution environments. Each record carries a monotonically increasing sequence number so removed records are detectable.

## Consequences
### Benefits
* Altering a single historical record breaks verification for that record and every subsequent record.
* Hardware-backed, non-exportable keys and attestation provide high technical assurance that records were generated by a device with genuine secure hardware, designed to support strict procedural documentation.
* Sequence numbers make gaps from deleted records visible.

### Trade-offs
* Database schema requires careful management; updating or deleting past records is prevented by design.
* Requires exception handling to manage StrongBoxUnavailableException on budget Android devices.
* **Known limit:** the chain is tamper-evident, not tamper-proof. A rooted device could delete the newest records or rebuild an unsigned chain. Mitigations are signatures plus attestation, and optional off-device anchoring of the chain head via sync (see PRD §6).
* Offline attestation chain validation needs a bundled trust anchor; without it, validation is best-effort and flagged as such.
